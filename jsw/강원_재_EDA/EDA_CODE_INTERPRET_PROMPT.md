# 강원도 산불 EDA 코드·해석 작성 프롬프트

## 0. 이 파일의 목적

이 프롬프트 파일은 `산불 강원도 EDA` 프로젝트에서 분석 ID별로 다음 두 작업을 수행할 때 사용한다.

1. **코드 작성**

   * 사용자가 요청한 분석 ID에 대해 Jupyter Notebook에 그대로 append해서 실행 가능한 Python 코드 셀을 작성한다.

2. **해석 작성**

   * 사용자가 실행 결과를 전달하면, 해당 Step 진행예정로그에 붙여넣을 수 있는 해석문을 작성한다.

이 파일은 세션 시작용 프롬프트가 아니다.
작업 경로, 대상 노트북, 대상 로그, 현재 Step, 현재 분석 ID는 사용자가 세션 시작 시 별도로 입력한 지시와 업로드한 파일을 따른다.

---

## 1. 공통 전제

사용자는 로컬 Jupyter Notebook에서 코드를 직접 실행한다.

따라서 실행 권한이 없는 환경에서는 다음을 지킨다.

* 코드를 직접 실행한 것처럼 말하지 않는다.
* 플롯을 직접 열어본 것처럼 말하지 않는다.
* 실행 결과를 추정해서 해석하지 않는다.
* 사용자가 전달한 표, 출력, traceback, 플롯 확인 내용만 근거로 해석한다.

실행 권한이 있는 환경에서는 다음을 지킨다.

* 코드를 처음부터 끝까지 실행해 error output이 없는지 확인한다.
* 저장한 핵심 플롯 이미지를 직접 열어 시각적으로 검토한다.
* 표의 수치와 플롯의 패턴이 일치하는지 확인한다.
* 실제로 확인한 내용만 로그 해석에 작성한다.

## 2. 매 요청마다 먼저 확인할 파일

코드 작성 또는 해석 작성 전에 반드시 아래 파일을 확인한다.

1. 현재 Step 진행예정로그 `.md`
2. 이전 Step 진행예정로그 `.md`
3. 현재 Step의 `.ipynb` 노트북
4. 데이터 설명 또는 파이프라인 설명이 들어 있는 `README.md`
5. 이 프롬프트 파일

현재 Step 진행예정로그에서 반드시 확인할 항목은 다음과 같다.

* 현재 Step의 목적
* 분석 ID 순서
* 요청된 ID의 분석 질문
* 분석 단위
* 모집단
* 비교집단
* 기간
* 통제조건
* 층화조건
* 매칭조건
* 제외조건
* 필수 결과표
* 필수 플롯
* 통과 조건
* 중단 조건
* 해석 제한
* 해석 기록 양식
* 다음 ID 반영사항

이전 Step 진행예정로그에서는 다음을 확인한다.

* 최종 통합 해석
* 현재 Step으로 넘긴 고정 배경
* 현재 Step에서 교란 또는 층화 기준으로 사용할 내용
* 재입증하면 안 되는 결론
* 과해석 방지 사항

## 3. 요청 모드 판정

사용자 요청을 아래 세 모드 중 하나로 판정한다.

### 3.1 코드 작성 모드

다음과 같은 요청이면 코드 작성 모드다.

```text
S1-02로 넘어가줘
S2-04 진행해줘
다음 ID 진행
이번 ID 코드 작성해줘
입력한 프롬프트 파일의 명령사항을 따라 코드 만들어줘
```

이 경우 해당 분석 ID 하나에 대한 실행 가능한 Python 코드 셀만 작성한다.

### 3.2 해석 작성 모드

다음과 같은 요청이면 해석 작성 모드다.

```text
S1-02 해석 작성해줘
결과 해석 작성
입력한 프롬프트 파일을 실행해서 해석 써줘
진행예정로그에 붙일 해석문 작성해줘
```

이 경우 코드를 작성하지 않는다.
사용자가 전달한 실행 결과와 플롯 확인 내용을 근거로 로그에 붙여넣을 해석문만 작성한다.

### 3.3 에러 수정 모드

다음과 같은 요청이면 에러 수정 모드다.

```text
에러났어
traceback은 이거야
KeyError가 났어
AssertionError가 났어
이 오류 고쳐줘
```

이 경우 traceback을 기준으로 원인을 진단하고, 기존 로딩 구조를 깨지 않는 수정 코드 셀을 작성한다.

# PART A. 코드 작성 프롬프트

## A-1. 코드 작성 전 필수 확인

코드를 작성하기 전에 반드시 다음을 확인한다.

1. 현재 분석 ID가 진행예정로그의 순서상 진행 가능한지 확인한다.
2. 이전 ID의 실행·표·플롯·해석·반영이 완료되었는지 확인한다.
3. 현재 ID의 분석 질문을 한 문장으로 확정한다.
4. 분석 단위, 모집단, 비교집단, 기간, 통제·층화·매칭·제외 조건을 확정한다.
5. 현재 노트북에서 이미 로딩된 데이터프레임과 변수명을 확인한다.
6. 이미 존재하는 데이터 로딩 셀을 다시 작성하지 않는다.
7. 이미 생성된 변수명과 데이터프레임을 우선 사용한다.
8. 존재하지 않는 컬럼명이나 변수명을 임의로 가정하지 않는다.
9. 컬럼명이 불확실하면 본 분석 코드보다 먼저 확인용 코드 셀을 작성한다.
10. 출력 경로는 현재 Step 진행예정로그의 기본 경로를 따른다.

---

## A-2. 코드 작성 핵심 원칙

코드는 사용자가 Jupyter Notebook에 그대로 append해서 실행할 수 있는 하나의 Python 코드블록으로 작성한다.

반드시 지킬 사항:

1. 한 번에 하나의 분석 ID 코드만 작성한다.
2. 다음 ID 코드는 작성하지 않는다.
3. 노트북에는 코드와 실행 결과만 남기고 해석 Markdown은 작성하지 않는다.
4. 모든 해석은 진행예정로그에만 작성한다.
5. 표와 플롯 파일명에는 분석 ID와 내용을 식별할 수 있는 이름을 포함한다.
6. 하나의 이미지 파일에는 하나의 핵심 플롯만 저장한다.
7. EDA는 질문에 답하는 표와 시각화를 중심으로 구성한다.
8. 각 플롯은 하나의 명확한 분석 질문을 가져야 한다.
9. 표와 플롯은 노트북 전체 재실행으로 재생성 가능해야 한다.
10. 임의의 조건 완화, 임의 표본 제외, 임의 결측 대체를 하지 않는다.
11. 조건 완화나 표본 제외가 필요하면 먼저 감사표에 기록하고 중단 또는 사용자 확인 대상으로 남긴다.
12. 통계적으로 유의하지 않거나 예상과 다른 결과가 나오더라도 결과를 숨기지 않는다.

## A-3. 코드 셀에 반드시 포함할 요소

분석 ID의 성격에 맞게 다음 요소를 포함한다.

### 1. 기본 설정

* 필요한 `import`
* warning 최소화
* 한글 폰트 또는 마이너스 깨짐 방지 설정
* 현재 분석 ID 변수
* 표 저장 경로
* 플롯 저장 경로
* 경로 생성 코드

### 2. 입력 데이터 감사

분석표와 플롯을 만들기 전에 다음을 감사한다.

* 사용 데이터프레임 존재 여부
* 주요 컬럼 존재 여부
* 행 수
* 사건 수
* 고유 ID 수
* 대조군 수
* 비교집단별 표본 수
* 분석 단위별 중복 키
* 결측 수와 결측률
* 기간 범위
* 셀 또는 공간 키 범위
* 매칭 키 위반 여부
* 누수 가능성
* 이전 ID 산출물 재사용 여부
* 재사용 파일 checksum 또는 행 수

### 3. 분석 단위 생성

현재 ID의 진행예정로그에 적힌 분석 단위를 따른다.

예시:

* 사건 단위
* 고유 `기상셀ID × 기준시각` 노출 단위
* 셀 단위
* 셀×월 단위
* 셀×일 단위
* 매칭 쌍 단위
* 날짜 block 단위
* 기후지형유형 층화 단위

동일 노출, 반복 셀, 반복 날짜, 매칭 재사용이 있으면 통계 표본을 중복 생성하지 않도록 감사표를 만든다.

### 4. 결과표 생성

가능한 경우 결과표에는 다음을 포함한다.

* 집단별 `n`
* 고유 사건 수
* 고유 노출 수
* 고유 날짜 수
* 고유 셀 수
* 평균
* 표준편차
* 중앙값
* IQR
* 분위수
* 차이
* 비율 차이
* 95% 신뢰구간
* 검정통계량
* 원시 p-value
* 다중비교 보정 q-value
* 효과크기
* bootstrap CI
* 민감도 분석 결과
* 통과 조건 여부

p-value만 저장하지 않는다.

### 5. 플롯 생성

진행예정로그의 필수 플롯을 만든다.

플롯은 다음을 지킨다.

* 하나의 파일에는 하나의 핵심 플롯만 저장한다.
* 제목, 축 이름, 단위, 범례를 명확히 표시한다.
* 비교집단 색상과 순서는 가능하면 기존 노트북의 공통 설정을 따른다.
* 분포 비교에는 boxplot만 단독 사용하지 말고 ECDF, violin, histogram, delta plot 등 필요한 보조 플롯을 고려한다.
* 매칭 분석은 원값 비교와 delta 비교를 구분한다.
* 지도 플롯은 좌표계, 경계, 미매칭 여부를 확인할 수 있게 만든다.
* heatmap은 행·열 순서를 명시한다.
* 풍향처럼 원형자료는 단순 산술평균 플롯으로 결론내리지 않는다.

### 6. 감사표와 통과 조건

코드 마지막에는 다음을 출력한다.

* 입력 감사표
* 분석 단위 감사표
* 중복·결측 감사표
* 비교집단 표본 수표
* 결과표
* 플롯 저장 경로표
* 통과 조건 점검표
* 다음 단계 진행 가능 여부

통과 조건을 만족하지 못하면 코드가 조용히 넘어가지 않도록 한다.
단, 무조건 `assert`로 중단하기보다, 가능한 경우 감사표를 출력하고 명확한 실패 메시지를 제공한다.

## A-4. 통계 및 불확실성 원칙

현재 Step 진행예정로그에 통계 방법이 지정되어 있으면 그 방법을 따른다.

지정이 없을 때의 기본 원칙:

1. 독립성 가정이 약한 반복측정 자료에서 단순 Welch t-test를 주 검정으로 쓰지 않는다.
2. 날짜, 셀, 매칭쌍, 노출 단위의 군집 구조가 있으면 block 또는 cluster bootstrap을 우선 고려한다.
3. 평균 차이만 보지 말고 중앙값, 분위수, 분포 겹침도 함께 본다.
4. 효과크기는 변수 성격에 맞게 산출한다.
5. 여러 변수나 여러 쌍을 비교하면 FDR 보정을 적용한다.
6. 관찰자료의 집단 차이를 인과 효과처럼 표현하지 않도록 결과표 명칭도 중립적으로 둔다.
7. 파생지수와 입력 기상변수를 독립 증거처럼 합산하지 않는다.
8. 참조 임계치나 외부 등급은 실제 강원도 위험등급으로 이름 붙이지 않는다.

````
# PART B. 해석 작성 프롬프트

## B-1. 해석 작성 전 필수 확인

해석을 작성하기 전에 다음을 확인한다.

1. 사용자가 전달한 실행 결과가 현재 분석 ID의 결과인지 확인한다.
2. 코드 실행 중 error output이 있었는지 확인한다.
3. 결과표 파일명과 플롯 파일명을 확인한다.
4. 결과표의 핵심 수치를 확인한다.
5. 사용자가 직접 확인한 플롯 패턴 또는 제공한 이미지 내용을 확인한다.
6. 플롯을 직접 확인하지 못한 경우, 플롯 패턴을 추정해서 쓰지 않는다.
7. 통과 조건이 만족되었는지 확인한다.
8. 중단 조건에 해당하는 결과가 있으면 다음 ID로 넘어가지 않는다고 기록한다.
9. 해석은 현재 실행 결과만 근거로 작성한다.
10. 이전 Step 결과는 배경 또는 교란 점검 기준으로만 연결한다.

---

## B-2. 해석 작성 원칙

해석 작성 시 반드시 지킬 사항:

1. 실제 표에 없는 수치를 쓰지 않는다.
2. 실행하지 않은 결과를 쓰지 않는다.
3. 직접 확인하지 않은 플롯 패턴을 쓰지 않는다.
4. p-value만으로 결론을 내리지 않는다.
5. 표본 수, 효과크기, 신뢰구간, 분포, 이상치, 한계를 함께 해석한다.
6. 관찰자료의 집단 차이를 인과 효과처럼 표현하지 않는다.
7. 상관관계를 원인으로 표현하지 않는다.
8. 평균 차이만 보고 분포 전체가 분리되었다고 쓰지 않는다.
9. 비유의 결과를 “차이가 없다”로 단정하지 않는다.
10. 효과크기가 작거나 불확실성이 큰 결과도 주요 질문과 관련되면 기록한다.
11. 분석 결과가 예상과 달라도 그대로 보고한다.
12. 이전 분석 결론과 맞추기 위해 현재 결과의 반대 신호나 예외를 생략하지 않는다.
13. 파생지수의 구조적 상관을 독립 증거처럼 표현하지 않는다.
14. 외부 참조 단계나 임계치를 실제 위험등급 또는 발생확률로 표현하지 않는다.
15. 현재 ID만으로 말할 수 있는 결론과 말할 수 없는 내용을 구분한다.
````

## B-4. ID별 필수 해석 내용

### 1. 분석 질문과 필요성

* 이번 ID가 답하려는 질문을 한 문장으로 명확히 적는다.
* 이전 Step 또는 이전 ID의 어떤 발견 때문에 이 분석이 필요한지 연결한다.
* 분석단위, 모집단, 비교집단, 기간, 매칭·층화·제외 조건을 적는다.

### 2. 사용한 산출물

* 근거로 사용한 결과표와 플롯 파일명을 모두 적는다.
* 각 파일이 어떤 질문을 확인하기 위한 것인지 짧게 연결한다.

### 3. 결과표에서 확인한 정량 근거

* 핵심 결과마다 실제 수치를 적는다.
* 가능한 경우 비교집단별 `n`, 대표값, 집단 차이 또는 비율 차이, 효과크기, 신뢰구간, 보정 q값을 포함한다.
* “높았다”, “차이가 컸다”, “유의했다”로 끝내지 말고 얼마나 차이 났는지 적는다.
* 통계적으로 유의하지 않은 결과와 효과크기가 작은 결과도 주요 가설과 관련되면 함께 적는다.

### 4. 플롯에서 직접 확인한 시각 근거

* 분포 중심, 분산, 중첩 정도, 꼬리, 이상치, 비선형성, 계절·권역별 방향 차이를 구체적으로 적는다.
* 표의 평균 차이가 일부 이상치 때문인지 분포 전체의 이동인지 구분한다.
* 플롯별로 실제로 보이는 패턴을 적는다.
* 보이지 않는 내용을 추정하지 않는다.

### 5. 표와 플롯의 통합 해석

* 정량 결과와 시각 패턴이 같은 결론을 지지하는지 설명한다.
* 통계적 유의성, 효과크기, 실질적 의미를 구분한다.
* 전체 비교 결과와 매칭·층화 결과가 다르면 계절, 권역, 셀, 시간대 등의 교란 가능성과 함께 설명한다.
* 상관관계나 집단 차이를 인과관계로 표현하지 않는다.

### 6. Step1 및 이전 ID와의 연결

* 이번 결과가 이전 Step의 배경 기후·지형·계절성 결과와 일치하는지, 수정하는지, 새롭게 추가하는지 적는다.
* 이전 ID와 결론이 다르면 어느 분석 설계 차이 때문에 달라졌는지 설명한다.
* 이전 Step 결과는 현재 Step에서 재입증할 결론이 아니라 교란 점검과 사전 질문의 배경으로만 사용한다.

### 7. 현재 재 EDA의 최종 판단

* 이번 ID만으로 말할 수 있는 결론을 2~4개로 정리한다.
* 산불 발생 원인, 발생확률, 위험등급, 정책 효과처럼 현재 설계로 확인할 수 없는 내용은 결론에서 제외한다.

### 8. 한계와 과해석 방지

다음 중 해당되는 한계를 구체적으로 적는다.

* 표본 불균형
* 반복측정
* 의사반복
* 매칭 실패
* 결측
* 중복 키
* 측정오차
* 공간조인 한계
* 공간 자기상관
* 시간 자기상관
* 다중공선성
* 파생변수 계산 구조
* 외부 참조 임계치
* 품질검토 대상 셀
* 플롯 미확인
* 실행 환경 차이

반드시 다음을 구분한다.

```text
해석 가능한 범위:
해석하면 안 되는 내용:
```

### 9. 발표용 상세 해석과 핵심 문장

최종 발표에서 그대로 사용할 수 있도록 다음 순서의 한 문단을 작성한다.

```text
질문 → 근거 수치 → 플롯 패턴 → 의미 → 한계
```

또한 팀원이 표나 그림을 보지 않아도 이해할 수 있는 핵심 문장 1~2개를 별도로 작성한다.

발표 문장에도 실제 수치를 포함한다.
과도한 인과 표현을 사용하지 않는다.

### 10. 추가 분석 판단과 다음 ID 반영

* 추가 분석이 필요한지 여부와 판단 근거를 적는다.
* 필요하면 `Sx-A01`, `Sx-A02` 형식으로 추가 ID를 등록한다.
* 추가 ID에는 다음을 포함한다.

  * 발견 근거
  * 추가 질문
  * 분석 단위
  * 필요 결과표
  * 필요 플롯
  * 판단 기준
  * 중단 또는 완료 조건
* 추가 분석이 필요하지 않으면 왜 기존 분석으로 충분한지 적는다.
* 다음 정규 ID 코드에 반영할 필터, 변수, 층화, 매칭, 민감도 분석을 구체적으로 적는다.
* 다음 ID 코드는 작성하지 않는다.

## B-5. 해석 품질 금지 기준

아래 표현 방식은 금지한다.

1. 실제 표에 없는 수치 작성
2. 실행하지 않은 결과 작성
3. 플롯에서 확인하지 않은 패턴 작성
4. “전반적으로”, “대체로”, “차이가 있다”, “중요하다”만으로 끝나는 결론
5. p-value가 작다는 이유만으로 차이가 크다고 표현
6. 평균값만 보고 분포 전체가 분리되었다고 표현
7. 비유의 결과를 “차이가 없다”로 단정
8. 상관, 회귀계수, 집단 차이를 인과 효과로 표현
9. FWI 입력 구조를 독립적인 물리 검증 증거로 표현
10. 참조 임계치나 외부 등급을 실제 위험등급 또는 발생확률로 표현
11. 이전 분석 결론에 맞추기 위해 현재 결과의 반대 신호 생략
12. 플롯을 확인하지 않았는데 “플롯에서 확인된다”고 표현
13. 매칭 실패나 중복 키 문제가 있는데 다음 단계 진행 가능하다고 표현
14. 통과 조건 미충족을 한계로만 처리하고 중단 조건 여부를 판단하지 않는 것

# PART C. 에러 수정 프롬프트

## C-1. traceback 처리 원칙

사용자가 traceback을 전달하면 다음 순서로 처리한다.

1. 에러가 발생한 분석 ID를 확인한다.
2. traceback에서 에러 종류와 발생 라인을 확인한다.
3. 기존 로딩 구조를 깨지 않고 원인을 진단한다.
4. 존재하지 않는 컬럼 또는 변수명을 임의로 대체하지 않는다.
5. 먼저 실제 컬럼과 변수 상태를 확인하는 코드를 작성한다.
6. 필요한 경우에만 수정된 분석 코드 셀을 다시 작성한다.
7. 수정 이유를 코드 주석으로 남긴다.
8. 이전 산출물을 덮어쓸 경우 같은 분석 ID의 파일명을 유지하되, 감사표에 재실행 사실을 남긴다.

## C-2. 자주 발생하는 에러 대응

### KeyError

* 실제 컬럼 목록을 출력하는 확인 코드를 먼저 작성한다.
* 유사 컬럼명을 자동으로 가정하지 않는다.
* 컬럼명이 다르면 진행예정로그와 README, 노트북 로딩 셀의 정의를 기준으로 수정한다.

### NameError

* 기존 노트북에서 해당 변수가 생성되는지 확인한다.
* 로딩 셀 재작성보다 기존 로딩 셀 실행 여부 확인 코드를 우선한다.

### AssertionError

* assert 조건이 왜 실패했는지 감사표로 출력한다.
* 조건 자체가 잘못된 것인지, 입력 데이터가 잘못된 것인지 구분한다.
* 통과 조건을 임의로 완화하지 않는다.

### Merge 또는 Join 오류

* 조인 키의 dtype, 결측, 중복, 유일성을 감사한다.
* 조인 전후 행 수 변화를 표로 저장한다.
* many-to-many 조인이 생기면 통계 표본 중복 생성 여부를 먼저 확인한다.

### Plot 오류

* 플롯에 필요한 컬럼, 좌표계, 범주 순서, 결측 여부를 확인한다.
* 플롯 저장 경로가 존재하는지 확인한다.
* 지도 플롯은 CRS를 먼저 감사한다.

```
## F. 최우선 원칙

분석 결과를 원하는 방향에 맞추지 않는다.

현재 실행 결과가 가설과 다르거나, 효과크기가 작거나, 통계적으로 유의하지 않거나, 플롯에서 분포가 크게 겹치더라도 그대로 보고한다.

이 EDA의 목적은 결론을 만들어내는 것이 아니라, 분석 단위·비교집단·통제조건에 따른 관찰 패턴과 한계를 정확히 기록하는 것이다.
```
